# Segurança básica: autenticação, refresh token e dono por criador — Plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans para implementar task a task. Os passos usam checkbox (`- [ ]`).

**Goal:** Login com JWT de acesso (15 min) e refresh token em cookie `httpOnly`; cada caixa, cabo, OLT e cliente guarda o criador; só o criador altera ou apaga, e só `ADMIN` gerencia usuários.

**Architecture:** Spring Security stateless com filtro JWT. O refresh token é aleatório, guardado como hash em `refresh_token` e rotacionado a cada uso. Um `OwnershipGuard` centraliza a regra de dono, chamado pelos services de escrita.

**Tech Stack:** Spring Boot 4.1.2, Spring Security, jjwt 0.12.x (versão a confirmar: pelo menos 2 semanas de idade), BCrypt, Flyway, Testcontainers.

**Spec:** `docs/superpowers/specs/2026-11-20-security-design.md`

## Global Constraints

- Schema só via Flyway; a próxima migration é `V8__security.sql`. Não editar V1 a V7.
- `ddl-auto=validate`: toda entidade nova ou alterada exige a migration.
- Erros em ProblemDetail (`ServiceErrors`): `401` sem token ou com token inválido, `403` sem permissão.
- Access token: 15 minutos. Refresh token: 14 dias. Cookie `geofiber_refresh`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth`.
- Sem commit: o `CLAUDE.md` exige que o usuário peça. Deixar tudo no working tree.
- Documentação em português (`SPECS.md`, `API.md`); código em inglês.

## Review Focus

Entradas e falhas que o desenho sugere e que nenhuma task cobre sozinha. Cada uma tem teste na task dona do código.

1. **Reuso de refresh token já rotacionado** (sinal de roubo): deve revogar todos os refresh tokens do usuário. Task 5.
2. **Token de acesso adulterado, expirado ou malformado**: deve dar `401`, nunca `500`. Task 4.
3. **Login com e-mail inexistente e com senha errada**: mesma resposta, para não revelar quais e-mails existem. Task 5.
4. **Usuário desativado com access token ainda válido**: vale até 15 min; o refresh falha imediatamente. Task 6.
5. **Ligar elemento de dono A a elemento de dono B por um terceiro**: deve dar `403`. Task 9.

### Task 5: Login, refresh com rotação e logout

**Files:**
- Create: `services/auth/AuthService.java`, `controllers/auth/AuthController.java`, `dto/auth/LoginRequest.java`, `dto/auth/TokenResponse.java`
- Test: `src/test/java/.../auth/AuthIT.java`

**Interfaces:**
- Produces: `AuthService.login(email, password) -> AuthTokens(String accessToken, String refreshToken)`; `AuthService.refresh(String rawRefresh) -> AuthTokens`; `AuthService.logout(String rawRefresh)`.
- Endpoints: `POST /api/v1/auth/login` (corpo `{email, password}`; devolve `{accessToken, expiresIn}` no corpo e o refresh em `Set-Cookie`), `POST /api/v1/auth/refresh` (lê o cookie), `POST /api/v1/auth/logout` (revoga e expira o cookie).
- Refresh token: 32 bytes aleatórios em Base64URL; guardado como SHA-256 do valor.
- Erros: login inválido → `401` com a mesma mensagem para e-mail inexistente e senha errada; refresh sem cookie, expirado ou revogado → `401`.

- [ ] **Step 1: Write the failing tests**:
  - login correto devolve access token e `Set-Cookie` com `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`;
  - login com e-mail inexistente e com senha errada devolvem o mesmo corpo;
  - refresh devolve novo par e revoga o anterior;
  - **reuso**: apresentar o refresh antigo depois de rotacionado devolve `401` e revoga todos os refresh tokens do usuário (um novo refresh, com o token válido de antes, também falha);
  - logout revoga o token atual.

- [ ] **Step 2: Run test to verify it fails.** Expected: FAIL.

- [ ] **Step 3: Implement** `AuthService` com `@Transactional`. Na rotação, o token antigo recebe `revokedAt` e o novo é criado na mesma transação. Comparação do hash em tempo constante (`MessageDigest.isEqual`).

- [ ] **Step 4: Run test to verify it passes.** Expected: PASS.
